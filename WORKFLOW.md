# WORKFLOW.md — как устроен и как запускать проект

Простыми словами о том, из чего состоит сайт (поиск медуслуг/клиник, запись на приём) и как с ним работать.

## Из чего состоит проект

Два отдельных git-репозитория в одной папке:

- **`backend/`** — Django + Django REST Framework. Хранит данные (клиники, услуги, врачи, записи) и отдаёт их через API. Плюс встроенный AI-ассистент (LangChain + OpenAI), который умеет искать клиники/услуги и записывать на приём прямо в чате.
- **`frontend/`** — React + TypeScript (Vite). Сайт, который видит пользователь: списки клиник и услуг, страница клиники, форма записи, чат с ассистентом.

Фронт всегда обращается к бэкенду через API (`VITE_API_BASE_URL`, по умолчанию `http://localhost:8000/api`). Без запущенного бэкенда фронт не сможет ничего показать.

## Как всё запустить локально

### 1. Бэкенд

```bash
cd backend
python -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env        # и впиши свой OPENAI_API_KEY, если нужен AI-ассистент
.venv/bin/python manage.py migrate
.venv/bin/python manage.py createsuperuser   # чтобы был доступ в админку
.venv/bin/python manage.py runserver
```

Бэкенд поднимется на `http://localhost:8000`.
- API: `http://localhost:8000/api/`
- Админка (добавлять клиники/услуги/врачей): `http://localhost:8000/admin/`
- Документация API: `http://localhost:8000/api/docs/` (Swagger) или `/api/redoc/`

Без `.env` бэкенд всё равно запустится с дефолтными dev-настройками и локальной базой SQLite (`db.sqlite3`).

### 2. Фронтенд

Открой второй терминал:

```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```

Сайт поднимется обычно на `http://localhost:5173`.

**Важно:** бэкенд должен быть уже запущен, иначе фронт не получит данные.

## Как устроены данные (бэкенд)

Всё живёт в одном Django-приложении `clinics`:

- **Клиника (Clinic)** — название, город, адрес, телефон, часы работы.
- **Услуга (Service)** — принадлежит клинике, есть название и цена.
- **Врач (Doctor)** — принадлежит клинике, оказывает набор услуг (только те, что есть у этой же клиники), может быть фото.
- **Запись на приём (Appointment)** — пациент, клиника, врач, услуга, желаемые дата/время, статус:
  - `pending` — ожидает подтверждения (создаётся автоматически при записи через сайт),
  - `confirmed` — подтверждена (меняется только в админке),
  - `cancelled` — отменена.

Систeма не даёт записать одного и того же врача на одно и то же время дважды (проверяется и на уровне формы, и на уровне базы данных).

Управлять клиниками/услугами/врачами и подтверждать/отменять записи можно **только через админку** (`/admin/`) — обычные посетители сайта этого делать не могут.

## Как устроен сайт (фронтенд) — страницы

| Путь | Страница | Что делает |
|---|---|---|
| `/` | Главная (HomePage) | Стартовая точка, обзор/навигация |
| `/services` | Список услуг (ServicesPage) | Поиск и просмотр услуг по всем клиникам |
| `/clinics/:id` | Клиника (ClinicDetailPage) | Подробности клиники: услуги, врачи |
| `/booking/:clinicId` | Запись (BookingPage) | Форма записи на приём в конкретную клинику |
| `/assistant` | AI-ассистент (AssistantPage) | Чат, где можно спросить про клиники/услуги и записаться словами, а не формой |
| `*` | 404 (NotFoundPage) | Любой неизвестный адрес |

## Типичные пользовательские сценарии

**Сценарий 1 — запись через форму:**
1. Пользователь заходит на `/services`, ищет нужную услугу.
2. Открывает клинику (`/clinics/:id`), смотрит врачей и услуги.
3. Переходит на `/booking/:clinicId` и заполняет форму (имя, телефон, дата/время, услуга/врач).
4. Запись создаётся со статусом `pending`.
5. Администратор в `/admin/` подтверждает или отменяет запись.

**Сценарий 2 — запись через AI-ассистента:**
1. Пользователь заходит на `/assistant` и пишет, что ему нужно (например, "хочу записаться к стоматологу в четверг").
2. Ассистент сам ищет клиники/услуги через свои инструменты и уточняет недостающие детали (имя, телефон, дата/время).
3. Когда всех данных достаточно, ассистент создаёт запись напрямую (та же логика, что и в форме — двойная запись на одно время невозможна).

Для работы ассистента обязательно нужен `OPENAI_API_KEY` в `backend/.env`, иначе `/api/assistant/chat/` не будет отвечать.

## Деплой (Railway)

- **Бэкенд**: подробности в `backend/README.md`. Нужен Postgres-сервис, переменные `SECRET_KEY`, `DEBUG=False`, `ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, при необходимости `OPENAI_API_KEY` и S3-переменные (фото врачей на Railway не сохраняются между деплоями без S3).
- **Фронтенд**: подробности в `frontend/README.md`. Собирается как статика (`npm run build`) и раздаётся через `serve`. `VITE_API_BASE_URL` нужно задать **до сборки** (build-time переменная), иначе в собранном коде останется адрес локального бэкенда.
